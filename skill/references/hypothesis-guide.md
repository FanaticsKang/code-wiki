# 工作假设指南（hypothesis-guide）

本文档定义 `wiki/hypothesis.md` 的用法。hypothesis.md 是 agent 对这个项目**当前的心智模型**——不是产出，是**工作草稿**，会被不断重写。它的存在是为了让每次扫描都带着全局视角，而不是退化成线性的文件遍历。

## 这不是什么

- **不是** architecture.md 的草稿。architecture.md 是给用户读的、经过验证的结论；hypothesis.md 是给 agent 自己用的、**允许出错**的猜测。
- **不是** 累积式文档。它是**会被整段重写**的，旧版本通过 log.json 里的"hypothesis v2 → v3 变更摘要"保留历史。
- **不是** TODO 列表。它是对"这个项目是什么、核心在哪、数据怎么流"的**当前最佳猜测**。

## 生命周期

hypothesis.md 的版本号随扫描推进：

- **v1**：init 阶段的浅层概览之后立刻产出。基于 README、目录结构、构建文件、几个入口文件的浅读。**大部分内容会是"猜测"而非"确认"**，这是预期的。
- **v2, v3, ...**：每批扫描后的反思步骤中，如果有任何假设被验证或推翻，递增版本。
- **收敛**：扫到后期，hypothesis 的改动会越来越小。当连续 2-3 批扫描都没有触发实质性修改时，说明心智模型已经稳定，可以开始把 hypothesis 的内容固化进 architecture.md。

## 模板

初始化时按以下模板创建 `wiki/hypothesis.md`：

```markdown
---
version: 1
last_updated: <YYYY-MM-DD>
confidence: low  # low | medium | high
---

# 工作假设 v1

> 本文档是 agent 对项目的当前心智模型。允许出错，会被不断重写。
> 用户可以随时阅读和纠正，但不要当成正式文档。

## 这个项目是什么（一句话）

<基于 README 和目录结构的猜测>

## 核心抽象（我当前的猜测）

> 列出 3-7 个我认为是"系统脊柱"的概念。每个一两行。标注置信度。

- **<抽象名 1>**：<一句话说明它在系统里的角色>（置信度：低/中/高）
- **<抽象名 2>**：...

## 核心数据流（我当前的猜测）

> 用一段话或 mermaid 描述"数据从哪进，经过什么，到哪去"。
> 如果还完全没头绪，写"尚不清楚"并列出"我需要看什么才能回答"。

<数据流描述或"尚不清楚 + 需要看什么">

## 我还不确定的

> 列出 3-10 个具体问题。每一个都应该是可以通过读某类文件来回答的。

- [ ] <问题 1>（候选答案在：<推测的文件/目录>）
- [ ] <问题 2>（候选答案在：...）

## 我预期会看到但还没看到的

> 根据当前假设推断"如果这个假设对，应该存在的东西"。如果扫到后期都没看到，说明假设有问题。

- 一个 `<推测的类名>` 类
- 某种形式的 `<推测的机制>`

## 本轮（下一批扫描）将重点验证

> 具体列出下一批要读哪些文件、重点回答哪几个"还不确定的"问题。

- 读 `<文件>`：验证 <问题>
- 读 `<文件>`：验证 <问题>

## 已确认（迁移自"还不确定的"）

> 扫描中被证实的假设。等 hypothesis 收敛时，这部分会被整理进 architecture.md。

_暂无_

## 已推翻

> 扫描中被否定的假设。记录"原来以为 X，实际是 Y"——这些是最有价值的洞察，往往指向项目的反直觉设计。

_暂无_
```

## 每轮更新规则

每批扫描结束时，主 agent 必须走一遍以下步骤，不是可选的：

1. 对照本批发现，逐条过"还不确定的"

   对每一个 `[ ]` 条目，判断：
   - 已回答 → 从"还不确定的"移到"已确认"，写清楚答案是什么、证据在哪个文件
   - 部分回答 → 改写问题，让它更具体
   - 不变 → 留着

2. 对照本批发现，检查"核心抽象"

   对每一个抽象：
   - 证实了 → 置信度上调（低→中→高）
   - 被推翻了 → 从"核心抽象"移到"已推翻"，并写新的抽象替代它
   - 发现新的核心抽象 → 追加到"核心抽象"，置信度"低"

3. 对照本批发现，检查"核心数据流"

   数据流是最容易被推翻的部分，因为它涉及多个文件的协作。问：
   - 本批读到的文件在我描述的数据流里的位置对吗？
   - 有没有一条我完全没考虑到的数据流？（例如异步事件流、定时任务流）
   - 边界点（入口、落地）我原来画对了吗？

   如果数据流需要改，**整段重写**，不要追加。旧版本通过 version bump 和 log 保留。

4. 检查"预期会看到但还没看到的"

   - 本批有没有看到预期中的东西？看到了就划掉。
   - 本批看到的东西里，有没有"预期应该有但我没列出来"的？补上。
   - 扫到后期（进度 > 60%）还没看到的预期，很可能是假设错了——要质疑相关的核心抽象。

5. 决定下一轮读什么

   清空"本轮将重点验证"，根据更新后的"还不确定的"和置信度较低的抽象，写下一轮的阅读目标。

   **不要按文件系统顺序决定**——按"读什么最能压缩不确定性"决定。

6. 版本 bump + 写 log

   - version + 1
   - last_updated 更新
   - confidence：根据"已确认"占比和"核心抽象"的平均置信度综合判断
   - 在 log.json 追加一条记录，描述本次 hypothesis 的关键变化（哪些被证实、哪些被推翻、新增哪些）

## 注入规则：谁能看到 hypothesis.md

hypothesis.md 是整体感的载体，必须注入到所有会做"提炼判断"的 prompt 里。

### 必须注入的场景

- 每次派发 sub-agent 扫描文件：在 prompt 的 preamble 里嵌入 hypothesis.md 的完整内容
- 主 agent 自己处理 sub-agent 汇报时：主 agent 的上下文里应该始终有最新的 hypothesis
- query 工作流：回答用户问题前先读 hypothesis，避免给出和当前心智模型冲突的回答
- lint 工作流：检查 wiki 内容和 hypothesis 是否一致

### 不需要注入的场景

- scan.py 的任何操作（它不做判断）
- 纯机械的 lint 检查（孤儿页、悬挂链接）

## sub-agent 应该如何使用 hypothesis.md

sub-agent 的 prompt 里会看到 hypothesis.md 的完整内容。它应该：

1. **带着假设去读文件**：读之前先问"根据 hypothesis，这个文件在系统里大概是什么角色？我预期会看到什么？"
2. **在汇报里明确回应假设**：汇报 JSON 里增加字段 `hypothesis_feedback`，说明：
   - `confirms`：本文件证实了 hypothesis 里的哪些点
   - `contradicts`：本文件和 hypothesis 冲突的点（这是最有价值的信号）
   - `new_observations`：hypothesis 里完全没提到但本文件暴露出来的东西
3. **不要盲目服从假设**：如果文件内容和假设完全不一致，信文件，不信假设。在 contradicts 字段里明确说"hypothesis 认为 X，但这个文件显示 Y"。

### sub-agent 汇报 JSON 的增量字段

```json
{
  "hypothesis_feedback": {
    "confirms": ["核心抽象 Executor 确实是调度中心，本文件的 Executor.run 是主循环"],
    "contradicts": ["hypothesis 认为数据流是 A→B→C，但本文件显示 A 可以直接跳到 C"],
    "new_observations": ["本文件暴露了一个 hypothesis 没提到的重要机制：事件总线"]
  }
}
```

主 agent 在反思步骤中，**必须优先处理所有 sub-agent 的 contradicts 字段**——这些是 hypothesis 需要修正的最强信号。

## 常见陷阱

- **写得太完美**：hypothesis v1 应该是"粗糙但全局"的，不是"初稿即定稿"。允许猜错，才能在修正时学到东西。
- **只追加不重写**：v2 不是在 v1 末尾加几行，而是整段重写核心抽象和数据流。
- **置信度虚高**：没有强证据之前，置信度应该保持"低"。整份文档的 confidence 不应该在扫描进度 < 30% 时就达到 "high"。
- **把 hypothesis.md 当成 architecture.md 的草稿**：不是。architecture.md 只写已确认的。hypothesis.md 允许包含猜测、甚至允许保留已知有问题的部分（只要标注置信度）。
- **扫到后期还在猛改**：如果扫描进度 > 70% 了，hypothesis 的核心抽象还在大改，说明要么前期读的顺序有问题（没先读核心），要么项目本身没有清晰骨架（这本身就是给用户的一个重要发现，写到 refactor.md）。
