# 反思检查清单（reflection-checklist）

每批 sub-agent 完成后，主 agent 必须走这个清单。**不是可选的**。这是让 wiki 保持整体感、避免退化成追加式流水账的核心机制。

## 什么算"一批"

- 按文件夹派发的一组 sub-agent 全部返回
- 或主 agent 决定"这是一个阶段"的停顿点（例如读完所有"核心入口"、读完所有"核心抽象的实现"）

批次粒度不必刚性。**宁可反思频繁一点，也不要攒一大堆再一起处理**——后者容易丢信号。

## 清单

严格按顺序走，不要跳。

### 步骤 1：收集冲突信号

读本批所有 sub-agent 汇报的 `hypothesis_feedback.contradicts` 字段。

- 如果**有任何 contradicts 条目** → 本批必须更新 hypothesis.md（走步骤 3）
- 如果**全部 confirms、无 contradicts** → hypothesis 可能只需要把对应"还不确定的"迁移到"已确认"，不需要大改
- 如果**有多个文件 contradicts 同一个点** → 这是强信号，对应的核心抽象/数据流几乎肯定需要重写

把所有 contradicts 列出来，按"涉及哪个核心抽象/哪条数据流"分组。

### 步骤 2：收集新观察

读本批所有汇报的 `hypothesis_feedback.new_observations`。

- 合并去重（多个文件可能观察到同一个东西）
- 判断：这些"新观察"里，有哪些**频繁出现**（≥2 个文件提到）？频繁出现的 = 很可能是 hypothesis 漏掉的核心抽象，要加进去。
- 低频观察（只有 1 个文件提到）留作"还不确定的"候选。

### 步骤 3：更新 hypothesis.md（如有必要）

如果步骤 1 或步骤 2 发现了实质变化，走 hypothesis-guide.md 的"每轮更新规则"完整流程。

**关键判断：是否需要重写核心数据流？**

数据流重写的触发条件（满足任一）：
- 本批发现了一条 hypothesis 里完全没提到的数据流（例如事件驱动、定时任务、回调链）
- 本批发现原来描述的数据流里缺了关键一步
- 本批发现原来的边界点（入口/出口）画错了

**重写意味着整段删掉重写，不是在后面加 update**。

### 步骤 4：检查已有页面的一致性

**这是最容易被忽略、也最重要的一步**。

列出本批发现可能影响的老页面（已经写完的 wiki 页）：

- 本批涉及的 modules 页 → 本批发现会不会改变"这个模块对外承担什么职责"的描述？
- 本批涉及的 concepts 页 → 本批发现会不会改变这个概念的定义或边界？
- 本批涉及的 algorithm 页 → 本批发现会不会改变这个算法的步骤、边界条件、复杂度？
- architecture.md → 本批发现会不会改变全局骨架的描述？

**对每个可能受影响的老页面，主 agent 必须重新读一遍**（不是凭记忆），然后判断：

| 情况 | 处理 |
|---|---|
| 本批发现和老页面**完全一致** | 什么都不做 |
| 本批发现是老页面的**有益补充**（不冲突，只是多了信息） | 追加一段，但如果追加导致老页面结构失衡，**整段重写** |
| 本批发现和老页面**局部冲突**（某个细节描述不对） | 改写冲突的部分，并在 refactor.md 的"疑问"区记一条让用户注意 |
| 本批发现和老页面**核心冲突**（老页面的主要论点错了） | **整段重写老页面**。不是 "update:" 追加，是重写。旧版本通过 git 保留。 |

**判断"有益补充"还是"需要重写"的标准**：如果一个新读者先读老页面再读追加段，会不会觉得"前面说的和后面说的不是一回事"？如果会，就要重写。

### 步骤 5：检查"预期但还没看到"

读 hypothesis.md 的"我预期会看到但还没看到的"。

- 本批看到了吗？看到了就划掉。
- 本批读了对应预期应该出现的文件/目录但没看到？**警报**——假设可能错了，在 hypothesis.md 的"已推翻"区记一条"预期 X 但未在 Y 处发现，假设可能需要修正"。

### 步骤 6：更新 refactor.md

本批所有汇报里的 refactor 条目，合并去重后追加到 refactor.md。

**但是**——check 一遍老的 refactor 条目：

- 有没有老条目被本批发现**隐含否定**了？（例如本批读到某处发现那个"可疑实现"其实是有意为之的，上下文是 X）
- 有没有老条目因为本批看到了更多代码，严重度应该**上调或下调**？

被否定或需要调整的老条目，改写或标记 `~~strikethrough~~`，不要直接删——保留记录表示"曾经怀疑过这里，后来澄清了"。

### 步骤 7：决定下一批读什么

读 hypothesis.md 的"本轮将重点验证"（在步骤 3 中你已经更新过了）。

具体列出：
- 下一批读哪几个文件
- 每个文件的阅读目标是回答哪个"还不确定的"问题
- 预期的批次大小

把这个决定写进 log.json 的本次 reflection 记录里。

### 步骤 8：写 log.json

追加一条结构化的反思记录：

```json
{
  "date": "<YYYY-MM-DD>",
  "action": "reflect",
  "batch_summary": "扫描了 core/dag/ 下 8 个文件",
  "hypothesis_version": {"from": 2, "to": 3},
  "key_changes": [
    "核心抽象 Executor 从'中'升到'高'置信度，证据：executor.py 主循环",
    "数据流整段重写：原认为是 A→B→C，实际发现 B 是事件驱动，A 直接 publish，C 是订阅者",
    "新增核心抽象 EventBus"
  ],
  "pages_rewritten": [
    "modules/core__dag.md (数据流部分整段重写)",
    "architecture.md (加入事件总线)"
  ],
  "pages_touched": [
    "concepts/节点状态.md (追加一段补充状态转换)"
  ],
  "refactor_changes": {
    "added": 4,
    "strikethrough": 1,
    "severity_adjusted": 2
  },
  "next_batch_plan": "读 core/events/ 验证 EventBus 的订阅者注册机制"
}
```

## 反思完成的标志

反思步骤的产出应该包括：

- [ ] hypothesis.md 已更新（或明确决定不需要更新）
- [ ] 所有 contradicts 已处理
- [ ] 所有老页面已检查一致性，需要重写的已重写
- [ ] refactor.md 已追加 + 已复查老条目
- [ ] 下一批的阅读计划已写入 hypothesis.md
- [ ] log.json 已追加反思记录

**所有 checkbox 打勾之前，不要派发下一批 sub-agent。**

## 反思的语言模式

反思步骤是 agent 和自己对话的时刻。推荐的思维模式：

**做得好的反思**（内心独白示例）：

> "本批 3 个文件都提到了 EventBus，但 hypothesis.md 完全没提。这不是小事——如果 EventBus 是核心通信机制，那我原来画的数据流 A→B→C 可能是表层，真正的流是通过 EventBus 解耦的。让我重读 modules/core__dag.md 的数据流部分……嗯，那段描述现在看起来太简单了，要整段重写。"

**做得不好的反思**（要避免）：

> "本批扫了 3 个文件，都完成了。追加到 log.json，继续下一批。"（问题：没有思考冲突、没有检查一致性、没有更新 hypothesis、把反思当成了流水账）

## 常见陷阱

- **追加主义**：只往页面末尾加东西，从不重写。扫到后期页面会变成"层累的地质沉积"，早期段落过时但还在那里误导读者。
- **乐观偏差**：倾向于把发现解读为"证实了假设"，忽略矛盾的细节。对 contradicts 字段要保持高敏感度。
- **反思流于形式**：机械地过清单，不真正思考。判断每一步：我这次做完之后，wiki 比之前是更连贯了，还是只是更多了？
- **跳过步骤 4**：最常被跳的一步。老页面不重读，新发现就接在新页里，久而久之新老分裂，同一个东西在不同页有不同描述。
