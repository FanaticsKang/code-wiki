# 初始化流程（workflow-init）

当用户首次让你为一个代码仓库建 wiki 时，按这个流程走。**不要跳步**，尤其不要跳过和用户的确认——在错误的方向上扫 100 个文件比多聊两分钟贵得多。

## 步骤 1：浅层概览

只读这些东西，**不读具体代码**：

- 仓库根目录的 `ls` 结果（`ls -la` 或 `view` 根目录）
- 根目录的 `README*`、`CHANGELOG*`、`CONTRIBUTING*`
- 构建/依赖文件：`package.json`、`pyproject.toml`、`requirements.txt`、`Cargo.toml`、`go.mod`、`pom.xml`、`build.gradle`、`Makefile`、`Dockerfile`、`docker-compose*`
- 配置入口：`.env.example`、`config/`、`settings.*`
- 顶层的目录结构（不展开到叶子，看一两层即可）

基于这些，回答给用户这几件事：

1. 这是个什么项目？（语言、框架、大致用途）
2. 主要目录在哪？看起来哪几个是核心，哪几个是辅助（测试、脚本、文档、示例、配置）？
3. 入口文件可能是哪个？
4. 有没有已有的架构文档？

## 步骤 2：和用户确认扫描计划

**不要省略这一步**。用你在步骤 1 看到的信息，向用户提出具体的问题，不要问开放式问题。例如：

- "我看到有 `src/`、`tests/`、`scripts/`、`examples/` 四个目录。我建议先扫 `src/`，`tests/` 后面如果需要再补，`scripts/` 和 `examples/` 跳过。你看行吗？"
- "你主要是想重构，还是想加功能，还是想理解清楚之后做决定？这会影响我在 concepts 页和 refactor.md 里的取舍。"
- "要不要一个文件一个文件停下来和你同步，还是先一批批扫完？"
- "有没有你特别关心或者特别不信任的目录/模块？"

如果用户没有强偏好，采用下面这套**默认策略**并告诉他你在用默认：

- 扫描范围：源码主目录（通常是 `src/`、`lib/`、`app/`、`pkg/`、`internal/`，或者如果项目是扁平的就是根目录下所有源码）
- 排除：测试、示例、脚本、自动生成的代码、第三方 vendor（脚本已经默认排除了常见的 `node_modules`、`vendor` 等）
- 节奏：先批量处理前 10-20 个入口/核心文件，然后停下来和用户一起看一遍 wiki 的效果，再决定是否继续

## 步骤 3：搭建 wiki 骨架

运行脚本：

```bash
python .code-wiki/scan.py init
```

这会：
- 创建 `wiki/`、`wiki/files/`、`wiki/modules/`、`wiki/concepts/`、`wiki/algorithm/`
- 创建 `.code-wiki/state.json`
- 扫描仓库，列出所有源码文件

然后**你手动**（用 `create_file`）创建下面这些骨架文件，每个都先写个最小内容：

### `wiki/README.md` —— 入口页

```markdown
# <项目名> Wiki

本 wiki 由 code-wiki skill 增量维护，用来帮助理解和重构 `<项目名>` 代码仓库。

## 快速导航

- [架构总览](./architecture.md) — 项目的整体骨架和数据流
- [重构清单](./refactor.md) — 坏味道、耦合点、重构建议
- [页面索引](./index.md) — 所有 wiki 页面的目录
- [处理日志](./log.json) — wiki 的增量更新记录

## 目录说明

- `files/` — 每个源码文件对应一页（或若干文件合页）
- `modules/` — 每个模块/目录的综合说明
- `concepts/` — 静态结构：数据结构、领域实体、设计模式、术语定义
- `algorithm/` — 动态过程：核心算法、数据处理流水线、关键计算逻辑

## 项目一句话介绍

<这里写你从 README 和根目录推断出来的一句话介绍>

## 当前覆盖情况

<占位：等第一轮扫描结束后再填，比如 "已覆盖 src/ 下的 15/42 个文件">
```

### `wiki/index.md` —— 内容目录

先给个空骨架：

```markdown
# 页面索引

> 按类别组织的所有 wiki 页面。每次新增或更新页面时，同步维护此文件。

## 架构 & 重构

- [架构总览](./architecture.md) — 项目骨架和数据流
- [重构清单](./refactor.md) — 坏味道和改进建议

## 模块（modules/）

<随扫描进度追加>

## 算法 & 数据处理（algorithm/）

<随扫描进度追加>

## 概念（concepts/）

<随扫描进度追加>

## 文件（files/）

<随扫描进度追加>
```

### `wiki/log.json` —— 处理日志

```markdown
# 处理日志

> 每条目以 `## [YYYY-MM-DD] <操作> | <对象>` 开头，方便 `grep "^## \[" log.json | tail -N` 查最近动作。

## [YYYY-MM-DD] init | <项目名>
- 初始化 wiki 骨架
- 扫描到 N 个源码文件（大文件 K 个）
- 扫描范围：<用户确认的范围>
- 重点关注：<用户提到的重点>
```

（把占位替换成真实值，日期用 `date +%Y-%m-%d` 拿。）

### `wiki/architecture.md` —— 架构总览

先给个空骨架，结构由 `page-templates.md` 定义，这里只先建出来。内容在扫到足够的核心文件后填：

```markdown
# 架构总览

> 本页在逐步扫描的过程中持续更新。初始阶段只有初步猜测，请结合最新的 log.json 查看。

## 当前理解程度

初始化完成，尚未扫描源码。本页内容将在扫描过程中逐步补全。

## 初步猜测（基于 README 和目录结构）

<写你在步骤 1 里得到的初步判断>

## 待回答的问题

- 入口是什么？
- 数据从哪里进，到哪里出？
- 哪些是核心模块，哪些是辅助模块？
- 外部依赖（数据库、队列、外部服务）有哪些？
```

### `wiki/refactor.md` —— 重构清单

```markdown
# 重构清单

> 扫描过程中记录的坏味道、可疑实现、耦合点、死代码、TODO 矛盾等。每一条要注明来源文件和行号（大致范围即可）。

## 严重（需要优先处理）

_暂无_

## 中等

_暂无_

## 轻微 / 代码风格

_暂无_

## 可能的死代码 / 未使用

_暂无_

## 疑问（需要和用户确认）

_暂无_
```

## 步骤 4：展示初次计划

骨架搭好之后，运行：

```bash
python .code-wiki/scan.py plan --limit 30
```

把输出展示给用户，告诉他：

- 你打算按这个顺序扫
- 大文件用了 `[LARGE]` 标记，会分批读
- 每扫完一个文件你会做什么（更新 files/modules/concepts/architecture/refactor）
- 是要你一口气扫到底，还是每 N 个停一次汇报

**得到确认后**，再进入扫描循环（见 `workflow-scan.md`）。

## 常见陷阱

- **别在用户没确认范围之前就开扫**。多问一句不会死。
- **别把根目录的 `README.md` 写进 `files/`**——那是项目自己的文档，不是你要总结的源码。
- **别在 architecture.md 里瞎猜后就不管了**——它是在扫描过程中持续更新的，不是一次性写死的。
- **如果仓库非常小（< 20 个源码文件）**，可以跳过 modules 层，直接 files + concepts 就够了。告诉用户你这么干。
- **如果仓库是 monorepo**，和用户确认是按顶层子项目分别建 wiki，还是统一一个 wiki 分 modules。默认建议前者。
