# 重构导向指南（refactor-guide）

这个 skill 的一个核心使命是帮用户**理解屎山以便重构**。本文档讲：扫描时具体要找什么、怎么提炼数据流、怎么写出有用的重构建议。

## 心态

- 你不是在给代码写文档。你是在**替用户做"重构前侦察"**。
- 用户想知道的不是"这段代码做了什么"，而是"这段代码**为什么这样写**，**这样写有什么问题**，**拆开重写会不会踩坑**"。
- 屎山代码里 80% 的行是噪音，20% 的行是信号。你的任务是把信号捞出来，把噪音压缩。

## 扫描时要留意的信号

下面这些出现时，**立刻记到 refactor.md**（或相应的 concepts 页），不要等扫完再回想——你会忘。

### 架构级信号

- **双向依赖**：A 模块 import B，B 模块也 import A。这是循环依赖的先兆。
- **层级穿透**：本应分层的代码里，上层直接访问下层的下层（例如 controller 直接访问 db 而不是走 service）。
- **God 类 / God 函数**：单个类超过 500 行、单个函数超过 100 行——先不判断好坏，但一定要在 files 页里标出来。
- **全局可变状态**：模块级变量、单例里的可变字段、类变量被实例方法修改。
- **多个"入口"**：同一个功能有多个 API、CLI、任务等入口，且实现并不完全一致。
- **配置来源混乱**：硬编码常量、环境变量、配置文件、数据库里的配置，并存。
- **重复的基础设施**：同一个项目里两套日志系统、两套 HTTP 客户端、两套 ORM 用法。

### 逻辑级信号

- **注释和实现不一致**：注释说 "returns None on failure"，实际 raises。
- **错误处理吞异常**：`except: pass`、`catch (e) { }`、`rescue => nil`。
- **魔法值**：没有命名的常量（`if status == 7`、`sleep(42)`、`priority * 0.618`）。
- **深度嵌套**：超过 4 层的 if/for 嵌套。
- **长参数列表**：超过 6 个参数的函数。
- **布尔参数陷阱**：`foo(x, True, False, True)` —— 调用处完全不知道这些 bool 是什么意思。
- **重复代码**：近似相同的代码块出现 3 次以上，但没有抽出函数。
- **可疑的并发**：共享可变状态 + 没有锁、锁的范围过大、锁持有期间做 I/O。
- **资源泄漏嫌疑**：打开文件/连接/事务但没看到对应的关闭（尤其是在异常路径上）。
- **SQL 注入嫌疑**：字符串拼接 SQL。
- **不可信输入直接使用**：请求参数直接作为路径/命令/SQL/模板。
- **`TODO` / `FIXME` / `XXX` / `HACK`**：全都要记录，而且要判断是不是已经过期的 TODO（如果代码周围的上下文已经变了）。

### 死代码信号

- **从未被引用的导出**：用 `grep -r "function_name" src/` 在仓库内搜，返回 0 次就是嫌疑。
- **永远不会为真的分支**：`if False:`、注释掉的整段大段代码、`# deprecated` 但还留着。
- **废弃的参数**：参数被接收但函数体从不使用。
- **"历史遗留文件"**：整个文件没人 import。

### 测试 / 可观测性信号

这些信号如果发现了，记到 refactor.md 的"疑问"区，让用户决定是不是要补：

- 核心业务逻辑没有测试覆盖（可以用 `grep -l` 在 tests/ 里搜对应的源文件名）
- 没有日志，出了问题没法定位
- 日志过多，正常流程都在打 INFO 甚至 ERROR

## 提炼数据流的方法

屎山代码最容易让人迷路的地方就是"数据从哪里来到哪里去"。扫描时**主动追踪数据流**，而不是被动读代码。

### 方法：从边界往里追

项目的**边界**通常是：
- HTTP 路由入口
- CLI 命令入口
- 消息队列消费者
- 定时任务
- `main()` 函数

对每个边界入口，问自己：

1. **输入是什么**？请求体的 schema、命令行参数、消息格式、文件格式。
2. **第一次变换在哪里**？通常是参数解析、校验、反序列化。
3. **核心处理在哪里**？业务逻辑的主体。
4. **数据在哪里落地或对外输出**？写 DB、调外部 API、返回响应、写文件、发消息。
5. **中间经过了哪些"转手"**？每一次转手是一次潜在的信息丢失或不一致点。

把这条路径**画出来**（mermaid flowchart 或纯文字步骤）。**这条路径的归宿是 `algorithm/<流程名>.md` 页**（不是 concepts）——因为你写的是"一步步怎么处理"，是动态过程，不是静态结构。如果路径上暴露出多个独立的计算步骤（例如校验 → 打分 → 路由），每一步本身又有复杂度，可以各自再开一页 algorithm，主页面做为"总览"链过去。

### 方法：从输出往回追

有时候从入口往里追会迷失在分支里。反过来也行：选定一个"有意思的输出"（比如"这条 DB 记录是怎么写进去的"），用 `grep` 找所有写这个表/字段的代码，反向追溯调用栈。

```bash
rg "UPDATE users SET" src/     # SQL
rg "\.users\.update" src/       # ORM
rg "save_user|update_user" src/ # service 层
```

### 方法：数据结构对齐

项目里如果有多个"看起来相似但略有不同"的数据结构（`User` / `UserDto` / `UserView` / `UserRecord`），**列一张对齐表写进对应的 concepts 页**（数据结构对齐是静态结构性的信息，属于 concepts，不是 algorithm）：

| 字段 | User | UserDto | UserView | UserRecord |
|------|------|---------|----------|------------|
| id | ✓ (int) | ✓ (str) | ✓ (str) | ✓ (int) |
| email | ✓ | ✓ | ✓ | ✓ |
| password_hash | ✓ | ✗ | ✗ | ✓ |
| avatar_url | ✗ | ✓ | ✓ | ✗ |

这种表格能瞬间暴露出"我们到底有几个 User 概念、它们是怎么互相转换的"。通常也能暴露出若干个"多余的类型"。

**如果接着要问"这些类型之间具体怎么转换的"**——那就是一个 algorithm 页的素材（"用户数据的跨层转换"），和 concepts 页互相链接。记住分工：**concepts 写"有哪些、长什么样"；algorithm 写"怎么一步步变"**。

## 核心 vs 非核心：怎么分配注意力

扫描屎山时，**保护你的注意力**。下面这些东西**只写一句话或直接跳过**：

### 一句话处理的东西

- DTO / POJO / dataclass / struct：就是一堆字段
- Getter / setter：就是读写字段
- 格式转换：JSON ↔ dict、camelCase ↔ snake_case、日期格式
- 字符串模板 / 消息 i18n：就是一堆字符串常量
- 单纯的日志包装：`log.info(...)` 的薄包装
- 单纯的异常包装：把异常 A 转成异常 B 再抛
- 简单的配置加载：读环境变量 / yaml 的浅封装
- 简单的数据库 CRUD：没有业务规则的 SELECT/INSERT/UPDATE
- Protobuf / schema 生成的代码

**在 files 页里用极简版**，在 modules 页里不单独出段落，在 concepts 和 algorithm 页里都不出现。

### 要细读的东西

- 状态机、状态转换
- 权限/规则判断逻辑
- 缓存策略（填缓存、失效、命中/未命中分支）
- 并发控制（锁、信号量、channel、协程）
- 重试 / 超时 / 熔断 / 降级
- 事务边界
- 关键算法（排序、图、调度、解析器）
- 外部服务集成的"粘合层"（里面往往藏着很多 workaround）
- 错误恢复路径
- 启动/关闭流程（初始化顺序、资源获取顺序）
- 配置到行为的映射（"这个 flag 一开会发生什么"）

**这些要花力气**，细读后写进 files 的正常版，抽 concepts 页，必要时写进 architecture。

## 如何写一条好的 refactor 建议

模板见 `page-templates.md`，这里讲原则：

1. **位置要精确**：文件 + 大致行号（用 grep 结果就够，不用精确到 1）。
2. **问题要可验证**：别写"代码不好看"；要写"`_tick` 持锁做 I/O，锁持有时间 > 50ms"。
3. **影响要具体**：不写"可能影响性能"；要写"`submit` 调用的 p99 延迟会被 tick 周期放大"。
4. **建议要可行**：不写"应该重构"；要写"把锁缩小到只保护 `_queue`，I/O 移出锁外"。
5. **证据要指向源码**：引用行号，让用户能直接跳过去看。
6. **严重度要区分**：用户上来先看"严重"区。不要把所有东西都标严重。

**反例**：
> `scheduler.py` 的设计不够好，建议重构。

**正例**：
> `src/core/scheduler.py:95-150` `_tick` 持有全局锁贯穿整个 100ms 循环，锁内包含 DB 写入（行 120）。影响：所有 `submit` 调用在 tick 期间阻塞，p99 延迟受 tick 周期放大。建议：锁缩到只保护 `_queue` 读写，DB 写入移出锁外。

## 什么时候产出一页"重构建议"级别的 concepts 页

如果在扫描过程中发现某类重构值得深入展开（例如"用户数据模型的统一方案"、"配置系统的整合"），可以单独建一个 `concepts/重构建议_xxx.md` 页，写清楚：

- 现状：当前有几套实现、它们的差异、各自的用处
- 问题：为什么需要重构
- 选项：可能的几种重构方向
- 影响面：会影响哪些文件和模块
- 建议的下一步：用户可以先做哪一小步验证方向

这种页面非常有价值，因为它把"扫描 + 分析 + 建议"沉淀成了可直接参考的决策材料。

## 不要越权

- 不要给用户做重构决策。你给出现状 + 证据 + 选项，让用户决定。
- 不要修改源码。本 skill 是只读扫描器。
- 不要假装你看懂了其实没看懂的东西。诚实记录"尚不明确"比编一个解释好。
- 不要因为一个地方看起来烂就断言它是 bug。可能有你不知道的历史原因；把它记为"需要和用户确认"。
