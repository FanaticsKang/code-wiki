# 深度扫描流程（workflow-deep）

针对用户指定的内容或目录，进行算法和数据流的**深度**扫描。与 `workflow-scan` 的区别：scan 追求广度覆盖，deep 追求单点纵深——把一个模块/链路/算法从"知道它做什么"推进到"完全理解它怎么做的、为什么这么做、哪里有问题"。

## 适用场景

- 用户说"深入看 XXX"或"详细分析 XXX 的数据流"
- 用户对某个模块/算法/数据流有具体问题，现有 wiki 页面回答不了
- 用户准备重构某个模块，需要比现有 wiki 更细致的实现细节

**前置条件**：wiki 已完成 init 和至少一轮 scan（否则没有基础认知，deep 会退化为从零扫描）。

## 两阶段流程

```
阶段 1：深度阅读（循环）
    0. 定位相关 wiki 页面，向用户确认范围
    1. 派发 sub-agent，每个带着主题描述 + 写入 files 页要求（非冷启动）
    2. sub-agent 直接写入 files 页；主 agent 验证写入内容
    3. 复现评判检查，不满足"可复现"标准则回到步骤 1
    until 当前主题下所有函数满足复现标准

阶段 2：串联验证
    4. 尝试从头到尾串联所有相关内容
    5. 复现评判 + 完备性检查；如有遗漏/冲突/不可复现 → 回到阶段 1
    6. 整理最终文档，保存到 wiki/deep/ 目录
```

## 阶段 1：深度阅读

### 步骤 0：定位与确认

1. **读取现有 wiki**：先读 `hypothesis.md` 和 `index.md`，再读和目标相关的 modules、concepts、algorithm 页面。
2. **列出相关文档**：基于 wiki 内容，列出哪些已有页面和目标相关，每页简述当前覆盖到什么程度。
3. **向用户确认**：

```
AskUserQuestion:
  question: "我找到以下和目标相关的 wiki 页面，你看还需要补充什么？"
  multiSelect: false
  options:
    - label: "范围正确，开始深入"
    - label: "还需要加入 XXX"
```

如果用户指出遗漏的文件/目录/概念，补充进去，然后再确认一次。

### 步骤 1：派发 sub-agent

每个 sub-agent **必须带着本次任务的主题描述**，不能冷启动。prompt 结构：

```
## 深度扫描任务

### 主题
<本次 deep 扫描的核心问题或主题，1-3 句话。例如："V2 链路中 DomainData 的完整数据流——从 Prefill 到 PostProcess，数据命名如何变更、每个环节做了什么变换">

### 项目整体认知（来自 wiki/hypothesis.md v<N>）
<完整粘贴 hypothesis.md 当前内容>

### 本文件/目录的已知上下文
* 所属模块：<从 wiki 推断>
* 现有 wiki 页面摘要：<一句话，说明目前 wiki 对此文件/目录了解到了什么程度>
* 直接依赖（import/include）：<从源文件头部提取>
* 被本项目其他文件依赖：<如有，从已扫过的文件汇报里反查>

### 阅读期望
<具体列出本次深度阅读需要回答的问题。例如：>
1. 这个函数的完整算法流程是什么？每一步做了什么变换？
2. 数据在这个函数中的命名是什么？进入时叫什么、出去时叫什么？
3. 有哪些 hardcode 或特殊处理？为什么要这样做？

请逐函数分析，不要跳过任何有实质逻辑的函数。

### 直接写入 files wiki 页（核心要求）

你**必须**将详细分析结果直接写入对应的 files wiki 页面，而不是只返回汇报。流程：
1. 先用 Read 工具读取对应的 files wiki 页面（路径为 `wiki/files/<映射路径>.md`）
2. 在该页面中追加"深度分析"节（格式见下方"files 页深度分析模板"）
3. 写入后，再用 Read 工具确认写入成功

**复现评判标准（最高优先级）**：你写入的深度分析内容，必须详细到——"一个不熟悉此代码的工程师，仅根据 wiki 页面内容，就能正确复现该函数的算法"。这是衡量分析是否充分的唯一标准。如果达不到这个标准，说明分析不够深入，需要继续补充。

具体要求：
- 算法流程中的每一步，必须写明：输入是什么（变量名 + 数据类型 + 格式）、具体做了什么变换、输出是什么（变量名 + 数据类型 + 格式）
- 循环/条件分支的完整逻辑（循环变量、终止条件、分支条件、每个分支做了什么）
- 数学公式或坐标变换的完整表达式（不要只写"做了一次坐标变换"，要写明变换矩阵或公式）
- 数据命名的完整变更链：进入时叫什么 → 中间变量叫什么 → 出去时叫什么
- hardcode 的精确值、所在行号、影响范围
- 边界情况处理（空值、异常、特殊帧索引）
- 如果某个步骤你无法推断原因，标为"原因不明，需和用户确认"——这本身对用户就是有价值的信息
```

**sub-agent 类型选择**：和 scan 流程相同，按扩展名映射（Python → python-scanner，C/C++ → cpp-scanner，其他 → generic-scanner）。

**批次策略**：根据目标范围大小决定。
- 目标是 1-3 个文件 → 一次性全部派发
- 目标是一个目录（5-15 个文件）→ 按紧密程度分 2-3 批，每批 3-5 个
- 目标更大 → 先聚焦核心文件，再扩展到辅助文件

### 步骤 2：收集汇报，验证 wiki 页面补充

**核心改变：sub-agent 直接写入 files 页，主 agent 只做验证和补充**。

sub-agent 完成后返回的汇报格式（在 scan 汇报基础上扩展）：

```json
{
  "date": "<YYYY-MM-DD>",
  "action": "deep-scan",
  "file": "<相对路径>",
  "deep_topic": "<本次深度扫描的主题>",
  "status": "completed",
  "pages_written": ["<wiki 页面路径>"],
  "findings_summary": {
    "functions_analyzed": <N>,
    "hardcodes_found": <N>,
    "data_flow_segments": <N>,
    "cross_file_connections": <N>
  },
  "gaps_found": ["<发现的遗漏/不完整之处>"],
  "reproducibility_check": {
    "all_functions_reproducible": true/false,
    "non_reproducible_functions": ["<函数名>: <原因>"]
  },
  "hypothesis_feedback": {
    "confirms": [],
    "contradicts": [],
    "new_observations": []
  }
}
```

注意：汇报中不再包含 `function_details` 等详细内容——这些已经由 sub-agent 直接写入了 files 页。汇报只包含**元信息**（写了哪些页面、统计数字、遗漏、复现检查结果）。

#### 主 agent 验证流程

主 agent 收到汇报后，**必须逐一验证 sub-agent 写入的内容**：

1. **读取已写入的 files 页**，检查"深度分析"节是否已正确追加
2. **复现评判**：对每个函数的深度分析，问自己——"仅凭这段描述，我能否复现该算法？"如果答案是不能，则需要补充派发 sub-agent
3. **交叉引用验证**：sub-agent 报告的 `cross_file_connections`，检查对应 files 页是否已记录
4. **hardcode 验证**：检查 `refactor.md` 是否已追加对应的条目

如果验证发现 sub-agent 写入的内容不完整或有错误，主 agent 有两个选择：
- 小问题（缺一个 hardcode 标注、变量名遗漏）：主 agent 直接补充
- 大问题（整个函数分析不够深入、算法流程缺失关键步骤）：针对该文件补充派发 sub-agent

#### 补充到 algorithm 页

如果深度扫描发现了新的算法细节（步骤、边界条件、复杂度、不变量），更新对应 algorithm 页的"核心步骤"和"边界条件 & 坑"节。**不是追加**——如果旧描述和新发现冲突，整段重写。此步骤仍由主 agent 完成（sub-agent 不负责 algorithm 页）。

#### 补充到 modules 页

如果深度扫描改变了对模块职责的理解（例如发现某个模块还承担了之前没注意到的角色），更新 modules 页的"对外职责"节。此步骤仍由主 agent 完成。

#### 标记 hardcode

sub-agent 在写入 files 页时，**同时**在 `refactor.md` 中追加对应的条目。主 agent 验证时确认 refactor.md 已更新。格式：

```
### [日期] `<文件>:<行号>` — <hardcode/特殊处理描述>

**问题**：<具体的值/处理>，没有配置接口或解释。

**可能原因**：<推测>。如无法推断，写"原因不明"。

**建议**：<如果是 hardcode 建议提取为配置/常量；如果是特殊处理建议加注释或重构>。
```

### 步骤 3：检查完整性（复现评判）

每批 sub-agent 完成后，主 agent 必须逐文件检查。检查分两层：

#### 第一层：存在性检查

- [ ] 本主题下涉及的每个函数，files 页是否都有了"深度分析"节？
- [ ] 数据流的每一段，是否都记录了"数据命名变更"？
- [ ] 每个 hardcode / 特殊处理，是否都已标记？
- [ ] 跨文件连接是否都记录了？
- [ ] refactor.md 是否已追加对应条目？

#### 第二层：复现评判检查（核心）

对每个已写入的函数详解，主 agent 必须做**复现测试**：假设自己是不熟悉此代码的工程师，仅凭 files 页的深度分析内容，能否正确复现该函数的算法？

逐项检查：

- [ ] **算法流程是否可执行**：每一步是否有明确的输入（变量名+类型+格式）、变换操作、输出（变量名+类型+格式）？有没有"做了 X"但没写"怎么做 X"的步骤？
- [ ] **数学/变换是否可计算**：坐标变换、矩阵运算、滤波公式等是否给出了完整表达式？还是只写了"做了一次变换"？
- [ ] **循环/分支是否完整**：循环的起始值、终止条件、步长是否明确？分支的完整条件和每个分支的处理是否都写了？
- [ ] **数据命名链是否连续**：从函数入口到出口，每个中间变量是否都有记录？有没有突然出现的未解释变量名？
- [ ] **hardcode 值是否精确**：hardcode 是否写了精确值（而非"某个阈值"）和所在行号？
- [ ] **边界情况是否覆盖**：空值处理、异常情况、特殊帧索引（如 frame_id=0）是否有记录？

**判断标准**：
- 如果某个函数的深度分析**任一检查项不通过** → 该函数不满足复现标准，需要补充
- 补充方式：回到步骤 1，针对遗漏的函数补充派发 sub-agent，prompt 中明确说"函数 `<name>` 的深度分析不满足复现标准，缺少 XXX"

**遗漏判断的标准**：
- 某个函数在汇报中被提到但 files 页没有详细分析 → 遗漏
- 数据流在某一步断掉了（不知道中间经历了什么变换）→ 遗漏
- 某个 hardcode 只被提到但没有分析可能原因 → 遗漏
- 算法流程只写了"做了 X"但没写"怎么做 X" → 遗漏
- 坐标变换/数学运算没有写完整表达式 → 遗漏

## files 页深度分析模板

sub-agent 写入 files 页时，**必须**按以下模板追加"深度分析"节。此模板的设计目标：**仅凭此节内容，一个不熟悉代码的工程师就能正确复现该函数的算法**。

```markdown
## 深度分析：〈主题名〉

> 以下为 deep 扫描补充的逐函数详解，目标：可据此复现算法。

### `<函数名>` (行 XX-YY)

**作用**：一句话。

**函数签名**：`def func(arg1: Type1, arg2: Type2) -> ReturnType`

**算法流程**：

1. **步骤 1**：`<输入变量名>` (`<类型>`, `<格式/形状>`) → 做了什么 → `<输出变量名>` (`<类型>`, `<格式/形状>`)
   - 具体操作：……
   - 公式/变换：`<完整数学表达式或伪代码>`
2. **步骤 2**：`<输入变量名>` → 做了什么 → `<输出变量名>`
   - 具体操作：……
3. **步骤 N**：……

**循环/条件分支**：

- 循环 `for i in range(start, end, step)`：起始值、终止条件、步长、每次迭代做了什么
- 条件分支 `if <条件>`：<条件> 时做 A，否则做 B。每个分支的处理逻辑

**数据命名变更链**：

`<进入时名称>` → [步骤 1] → `<中间变量1>` → [步骤 2] → `<中间变量2>` → … → `<出去时名称>`

**hardcode / 特殊处理**：

- `行 ZZ`：`<精确值>` — <影响范围>。可能原因：<推测>。如无法推断，写"原因不明，需和用户确认"。

**边界情况**：

- `<空值/异常/特殊索引>` 的处理：……
- `<数据缺失>` 的处理：……

**复现检查**：仅凭上述描述，能否复现此函数？（是/否。如否，补充缺失部分）

---

### `<下一个函数>` (行 XX-YY)
...
```

### 模板使用说明

1. **函数签名**必须写明参数类型和返回类型——这是复现的入口条件
2. **算法流程**的每一步，必须用"输入 → 操作 → 输出"三段式描述，且标明变量名和数据类型/格式
3. **数学公式**必须完整写出，不能用"做了一次坐标变换"之类模糊描述。例如：
   - 不够：`global_to_local_coords(pos, ref, quat)` → VCS 坐标
   - 足够：`p_local = R(q) @ (p_global - p_ref)`，其中 R(q) 是四元数 q 的旋转矩阵，p_ref 是参考点
4. **循环/条件分支**不能只写"遍历所有帧"，必须写明循环范围、终止条件、每次迭代的具体操作
5. **数据命名变更链**必须从函数入口到出口完整串联，不能有跳跃
6. **边界情况**是复现时最容易出错的地方——空值处理、首帧特殊逻辑、数据缺失兜底——都必须记录

### 与已有 files 页内容的关系

深度分析节是**追加**在 files 页已有的概述/核心内容之后。已有内容保持不变，深度分析作为新的一级节（`## 深度分析：〈主题名〉`）追加。如果已有内容和新发现冲突，在深度分析节中注明冲突，不要修改原有内容（留待 lint 阶段统一处理）。

## 阶段 2：串联验证

### 步骤 4：从头到尾串联

基于阶段 1 收集的所有算法细节，**尝试从头到尾串联完整的数据流和算法链路**。

具体做法：
1. 从目标链路的入口开始，写出完整的数据流路径
2. 在每一步标注：数据在这一步叫什么名字、经历了什么变换、输出叫什么名字
3. 标注所有 hardcode 和特殊处理出现的位置
4. 标注所有跨文件边界

产出一份**串联文档**（初稿），包含：

```markdown
# 〈主题〉完整串联

## 入口
<从哪里开始，初始数据是什么格式、叫什么名字>

## 完整路径

### 步骤 1：〈函数名〉(文件:行号)
- 输入：`<数据名>` (<格式>)
- 处理：...
- 输出：`<数据名>` (<格式>)
- hardcode / 特殊处理：...

### 步骤 2：...
...

## 出口
<最终输出是什么格式、叫什么名字、被谁消费>

## 尚未串联的断点
<如果某一步的数据流向不明确，列在这里>
```

### 步骤 5：完备性检查

对串联文档做以下检查：

1. **遗漏检查**：有没有函数在阶段 1 被提到但串联文档里没出现？
2. **冲突检查**：阶段 1 的多个汇报之间有没有矛盾？同一段数据流在不同汇报中描述不一致？
3. **深度检查**：有没有步骤只写了"做了 X"但没写"怎么做 X"的？有没有 hardcode 只写了值但没分析原因的？
4. **命名连续性**：数据从一步到下一步，命名是否连续？有没有突然冒出一个没解释过的变量名？
5. **复现评判**（核心）：对串联文档中涉及的每个函数，检查对应 files 页的深度分析节——"仅凭 wiki 描述，能否复现该函数的算法？"重点检查：
   - 数学/坐标变换是否给出了完整公式？
   - 循环/分支的控制逻辑是否完整？
   - 中间变量名是否全部记录？
   - hardcode 是否有精确值？

**判断**：
- 如果发现遗漏/冲突/不够深入 → 回到阶段 1，针对具体问题补充阅读
- 如果确认完备 → 进入步骤 6

**回退的粒度**：不需要重做整个阶段 1，只针对发现的问题补充派发 sub-agent。prompt 中要明确说"上次分析在 XXX 处不完整，请补充 YYY"。

### 步骤 6：保存最终文档

将最终版串联文档保存到 `wiki/deep/` 目录下：

```
wiki/deep/
└── <主题名>.md
```

文件名用中文，和 algorithm/concepts 页的命名惯例一致。

文档结构：

```markdown
---
type: deep-analysis
topic: <主题名>
files:
  - <涉及的源码文件 1>
  - <涉及的源码文件 2>
created: <YYYY-MM-DD>
last_updated: <YYYY-MM-DD>
based_on:
  hypothesis_version: <N>
  scan_progress: "<完成数/总数>"
---

# 深度分析：〈主题名〉

> 一句话概括这个主题是什么、为什么需要深度分析。

## 背景

基于现有 wiki 的哪些认知，用户需要进一步了解什么。

## 完整算法/数据流串联

### 入口
...

### 完整路径
<步骤编号，每步包含：所在文件/行号、输入数据名/格式、处理逻辑、输出数据名/格式、hardcode/特殊处理>

### 出口
...

## 关键发现

### 算法细节
<在深度扫描中新发现的、之前 wiki 没有记录的算法细节>

### 数据命名变更全表
| 步骤 | 文件:函数 | 进入时名称 | 变换 | 出去时名称 |
|------|-----------|-----------|------|-----------|
| ... | ... | ... | ... | ... |

### hardcode / 特殊处理清单
| 位置 | 值/处理 | 可能原因 | 关联 refactor 条目 |
|------|---------|---------|------------------|

## 与现有 wiki 的关系

- 补充了 `files/<页>.md` 的函数详解
- 更新了 `algorithm/<页>.md` 的算法步骤
- 新增 refactor 条目 N 条

## 未解决的问题

<如果深度扫描后仍有无法推断的 hardcode 原因、不确定的数据流路径等，列在这里供用户确认>
```

保存后，更新 `index.md`，在新增的"深度分析（deep/）"分类下列出该文档。

最后在 `log.json` 追加一条：

## sub-agent 的深度阅读期望

深度模式和 scan 模式最大的区别是 sub-agent 的**阅读深度和写入职责**。scan 模式下 sub-agent 可以只给"一句话概括"并返回汇报，但 deep 模式下 sub-agent **必须逐函数展开，并直接写入 files wiki 页面**。

### 核心评判标准：能否复现

**唯一评判标准**：写入的深度分析内容，必须详细到——"一个不熟悉此代码的工程师，仅根据 wiki 页面内容，就能正确复现该函数的算法"。

如果达不到这个标准，说明分析不够深入，需要继续补充。这不是可选的——这是 deep 模式存在的基本价值主张。

### 必须记录的内容

| 内容 | 说明 | 复现必要性 | 示例 |
|------|------|-----------|------|
| 函数签名 | 完整参数+返回类型 | 必须知道输入输出才能开始复现 | `def process(data: Dict[str, np.ndarray], frame_idx: int) -> DomainData` |
| 函数作用 | 一句话 | 理解意图 | "将 DomainData 从 protobuf 反序列化为 Python dict" |
| 算法流程 | 逐步骤编号，每步含：输入变量名+类型+格式 → 具体操作 → 输出变量名+类型+格式 | 这是复现的主体 | "1. `raw_bytes` (bytes) → protobuf 解码 → `frames_proto` (Frames) → 2. 遍历 `frames_proto.frames` → 提取 `domain_field` → `domain_items` (List[DomainDataItem])" |
| 数学/变换公式 | 完整表达式，不是模糊描述 | 没有公式就无法正确计算 | "`p_local = R(q) @ (p_global - p_ref)`，R(q) 是四元数 q 的旋转矩阵" |
| 数据命名变更 | 进入→中间→出去的完整变量名链 | 必须知道每步变量名才能跟踪数据 | "`e2e_data_bytes` → `e2e_data_dict` → `domain_dict`" |
| 循环/分支完整逻辑 | 起始值、终止条件、步长、每个分支 | 复现时必须知道完整控制流 | "`for frame in frames[:max_frames]`，max_frames=120" |
| hardcode | 精确值 + 行号 + 可能原因 | 必须知道精确值才能复现相同行为 | "`SHARED_MEMORY_SIZE = 20 * (1024 ** 3)` (行 42) — 20GB" |
| 特殊处理 | 代码 + 可能原因 | 复现时必须处理同样的特殊情况 | "`if frame_id == 0: skip_validation` — 首帧无前帧参考" |
| 边界情况 | 空值/异常/特殊索引的处理 | 边界情况是复现最容易出错的地方 | "`raw_data 为 None 时默认 b''，反序列化得到空 Frames" |

### 可以省略的内容

- 纯 getter/setter
- 简单的字段映射（两边字段同名同类型）
- 日志打印语句
- 标准库调用（json.loads, os.path.join 等）

### 写入流程

sub-agent 对每个被分析的文件，执行以下操作：

1. **Read** 对应的 `wiki/files/<映射路径>.md` 页面
2. **在页面末尾追加** `## 深度分析：〈主题名〉` 节（格式见上方"files 页深度分析模板"）
3. **同时在 `refactor.md` 中追加** hardcode/特殊处理条目
4. **Read** 确认写入成功
5. **在汇报中报告** `pages_written` 和 `reproducibility_check`

### 自检问题

写入前，对每个函数的深度分析问自己：

- [ ] 仅凭这段描述，我能否写出该函数的等价实现？
- [ ] 如果某个步骤的输入数据类型或格式不清楚，我能正确构造输入吗？
- [ ] 如果有坐标变换，我能否根据描述正确计算结果？
- [ ] 如果有循环，我知道循环几次、每次做什么吗？
- [ ] 如果有 hardcode，我知道精确值吗？
- [ ] 如果有边界情况，我知道该怎么处理吗？

**任何一项答"否"，分析就不充分，需要继续补充。**

## 与其他 workflow 的关系

| workflow | 和 deep 的关系 |
|----------|---------------|
| init | deep 依赖 init + scan 的产出，不能在 init 之前使用 |
| scan | scan 建立广度，deep 建立纵深。deep 会在 scan 的 files 页上追加内容 |
| query | query 回答单个问题，deep 系统性地深挖一个主题。如果 query 发现 wiki 严重不足，可以建议用户转用 deep |
| lint | deep 完成后建议跑一次 lint，检查 deep 追加的内容和已有页面是否一致 |

## 常见陷阱

- **把 deep 当 scan 用**：deep 不是"更细的 scan"。scan 是广度优先覆盖，deep 是纵深挖掘一个主题。不要在 deep 模式下试图遍历整个项目。
- **冷启动 sub-agent**：sub-agent 必须带着主题和问题开始，否则会退化为 scan 级别的浅阅读。
- **sub-agent 只汇报不写入**：sub-agent 必须直接写入 files 页，不能只返回汇报让主 agent 转写——信息经手二次转写会丢失细节。汇报只包含元信息和复现检查结果。
- **只追加不验证**：阶段 2 的串联验证不能跳过。没有串联过的细节只是一堆碎片，串联后才能看到全貌。
- **忽略 hardcode 原因分析**：只记录"这里有个 hardcode"是不够的，必须尝试推断原因。即使推断不出来也要写"原因不明"——这本身对用户就是有价值的信息（表示这个 hardcode 没有注释、没有文档、可能是个隐患）。
- **过度扩展范围**：deep 的目标应该具体（"V2 链路中 DomainData 的完整数据流"），不要设得太宽（"整个 DataFlowV2"），否则会退化为又一遍 scan。
- **不满足复现标准就通过**：这是 deep 模式最核心的质量底线。如果某个函数的深度分析不能让一个不熟悉代码的工程师复现算法，就不算完成。常见的不达标情况：算法流程只写了"做了 X"没写"怎么做 X"、坐标变换没有完整公式、循环只写了"遍历所有帧"没写终止条件和步长、数据命名变更链有跳跃。
