# Figure Analysis Protocol

Figures are the highest-density information source in a paper — and the source LLM vision is *least* reliable on. This protocol exists because relying on visual parsing alone produces confident-but-wrong structural claims, which then poison the rest of the deepdive.

**The core rule: never trust a single source. Architecture and data-flow claims must be corroborated by at least two of {vision, caption+text, equations, code}.**

## Which figures to analyze deeply

Not every figure. Only:

1. Figures referenced in a confirmed innovation's `location_in_paper`
2. Figure 1 and Figure 2 (almost always architectural overview)
3. Any figure with a block diagram, data flow, or labeled architecture

Skip:
- Loss curves, accuracy bar charts (read trends only, don't extract numbers — the paper's tables have those)
- Qualitative sample galleries (images generated by the model, attention heatmaps) — knowing they exist is enough
- t-SNE / UMAP / embedding projections

## The three-source protocol

For each target figure, extract information from three independent sources, then reconcile.

### Source A: Vision (direct)

1. Render the PDF page containing the figure at **200 DPI minimum** (pdf-reading skill's rasterize function)
2. If the figure spans more than half the page, also render a zoomed crop of just the figure area
3. If the figure is complex (>8 labeled blocks or >2 levels of nesting), split it into sub-regions:
   - left half / right half
   - top row / middle row / bottom row
   - encoder side / decoder side
   Render each sub-region separately and analyze one at a time.

**Do not ask the model to "describe" the figure freely.** Fill a schema (see `figure_schemas.md`). Free description invites hallucination. Schemas force "I can't fill this field" honesty.

### Source B: Caption + in-text references

1. Extract the **full caption verbatim**. Captions are often dense and precise — "A → B → C, with residual connection from A to C" — and deserve careful reading.
2. Grep the paper for every sentence that references the figure:
   - `Fig. N`, `Figure N`, `Fig.~N` (LaTeX)
   - Also check for references to specific parts: "the left side of Figure N", "as shown in the dashed line in Fig. N"
3. Compile these into an ordered list. These sentences often contain the authoritative description the figure is *illustrating*.

### Source C: Adjacent equations

The equations immediately before or after a figure typically formalize what the figure depicts. Extract all numbered equations in the same subsection, and note which ones the caption or nearby text links to the figure.

Equations beat figures for precision. A figure showing "softmax attention" and an equation showing `exp(x) / sum(exp(x))` are consistent. A figure showing "attention" and an equation showing `sigmoid(x)` means the figure is approximate — trust the equation.

### Reconciliation

Fill the schema (see `figure_schemas.md`) with data from all three sources. For each field, note which source(s) confirmed it:

```yaml
- field: "connection from block B2 to block B5"
  value: "residual (add, not concat)"
  confirmed_by: [caption, equation_4]
  vision_says: "unclear — arrow could be either"
  confidence: HIGH  # two non-visual sources agree
```

Rules for confidence:
- **HIGH**: confirmed by ≥2 sources including at least one non-visual
- **MEDIUM**: confirmed by 1 source OR by vision + one other that partially agrees
- **LOW**: only vision, or sources disagree
- **UNRESOLVED**: no source is clear — flag for Stage 3 code verification

## The "low-confidence → code verification" pipeline

The most important use of figure analysis is not to *resolve* ambiguities in isolation, but to **generate a list of questions for Stage 3** to answer from code.

Every `LOW` or `UNRESOLVED` field becomes a code-verification task:
- "Figure shows LayerNorm before attention, but I'm not sure — check `forward()` in the attention class"
- "Figure shows gating with tanh, but arrows are ambiguous — check whether the gate output goes through `torch.tanh`"
- "Figure shows a skip connection — check whether it's `+` (residual) or `torch.cat` (concat)"

This is why Stage 2 comes before Stage 3 in the pipeline: **figure ambiguities should drive targeted code reading, not the other way around.**

## Handling specific figure types

### Architecture block diagrams (most common)

Use the `architecture_diagram` schema. Key fields:
- `blocks` (nodes with id, label, type)
- `edges` (from, to, edge_type: forward | residual | skip | gated | attention-qk | attention-v)
- `annotations` (dashed lines, color meanings, shape annotations)

Watch for:
- **Arrow direction** — vision frequently confuses this. Always cross-check with text.
- **Residual vs. concatenation** — `+` vs. `concat` have the same visual (merging arrows). Caption usually disambiguates.
- **Repeated blocks** — "Nx" notation means "repeat N times", don't interpret as N separate blocks.
- **Shape annotations** — `[B, L, D]` next to an arrow is data flow information, preserve it.

### Data-flow diagrams (pipeline figures)

Use the `data_flow_diagram` schema. Similar to architecture but emphasis on sequential processing and shape transformations. Preserve shapes exactly.

### Algorithm box / pseudocode

If the figure contains an Algorithm block (common in ML papers), this is *the most reliable figure type* — it's basically a formal spec. Transcribe it line by line. Don't treat it as a "figure" needing visual parsing.

### Attention visualizations

Usually not useful for reimplementation. Note which layers/heads are visualized and skip unless the paper makes a specific architectural point about them.

## Common failure modes to watch for

1. **Missed residual connections** — thin arrows that loop around blocks. Always ask: does this figure have residual connections? If caption doesn't say, check the equations for `x + f(x)` patterns.

2. **Misread connection direction** — especially in recurrent or cross-attention figures. Text usually disambiguates: "Q comes from X, K and V from Y" is more reliable than figure arrows.

3. **Missed repetition notation** — `×N`, `Nx`, or a stacked-cards visual means the block repeats. Missing this gives wrong layer counts.

4. **Color-coded information** — figures often use color to encode module type or origin. If the paper is in color, note the color of each block. This is sometimes the *only* place the paper specifies "these three blocks share weights."

5. **Legend-only information** — figures may have a legend in a corner that defines symbols. Always scan for a legend first.

## A minimal working example

**Figure 2 in the Flamingo paper (Gated Xattn-Dense)**

Vision extract (schema):
- Blocks: "Frozen LM block", "GATED XATTN-DENSE", gates labeled with `tanh(α)` and `tanh(β)`
- Edges: frozen LM output → xattn → gate → add back to LM; FFW → gate → add
- Annotation: "Initialized to 0 so path is closed at start of training"

Caption extract (verbatim): [caption says gates are initialized to 0 so the model behaves like the original LM initially]

Equation extract: `y = y + tanh(α) · attention(y, x)` and similar for FFW.

Reconciliation:
- Gate mechanism: HIGH confidence (all three sources)
- Zero initialization: HIGH confidence (caption + annotation)
- Whether α is scalar or per-head: UNRESOLVED — mark for code check in Stage 3

In Stage 3, code reading will resolve the last point (turns out α is a scalar per layer in the public implementation).
